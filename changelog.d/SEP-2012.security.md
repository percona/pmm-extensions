Settings-override secrets written from this release carry an explicit `extensions.enc.v1.` envelope marker at rest, so whether a stored value is already encrypted is read off its own format instead of inferred from the text — closing a case where an operator-chosen token that happened to look like ciphertext was skipped by the encryption migration and left in the clear. Rows written before this release carry no marker, keep decrypting unchanged, and are never rewritten, so there is no migration to run and nothing to do on upgrade. Rolling the code back across this release requires stripping the marker first, because a release predating the envelope reads a marked value as plaintext and would present it to a remote as a credential: `alembic --name inventory downgrade -1`, `alembic --name tasks downgrade -1`, and `alembic --name extensions downgrade extensions_main@-1` — the `extensions` track carries several branch heads, so a bare `-1` there downgrades an arbitrary one of them. That step only strips the marker: it needs no `ENCRYPTION_KEY`, decrypts nothing, and leaves the values encrypted, so it is safe to run on a deployment whose key has been rotated away. It is also only the first step of a rollback that crosses this release: at-rest encryption of secret values and of credential-URL passwords ship alongside it, so their downgrades — described in their own entries under this release — must run after this one before an earlier release can read these rows, and unlike the unmark step those do decrypt and need the `ENCRYPTION_KEY` the rows were written under.
