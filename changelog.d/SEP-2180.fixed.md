XtraBackup restores now apply the incremental chain: S3 (s3cmd and awscli) and GCS sources no longer restore only the full backup, local and SSH sources no longer fail with a TypeError when incrementals exist, and picking an incremental run as the source restores the full backup plus the chain up to that run. A chain that cannot be listed now fails the restore instead of restoring the full backup alone. Before MySQL is stopped, the restore reads each chain backup's `xtrabackup_info` and checks it is the expected full or incremental type; it does not check data-file completeness or LSN continuity, so a chain broken that way still fails at `xtrabackup --prepare`, after MySQL is stopped and the data directory replaced. Each incremental is copied to the restore's incremental destination path (default `/tmp/pxb_incrementals`) and decrypted and decompressed there before it is applied, so that path needs room for the largest incremental at its decompressed size plus its compressed files while they expand; the last one is left there after the restore. "Skip incrementals" with an incremental-run source now fails the restore with an error naming the source; pick its full backup instead. Restores also no longer fail reading backup metadata on hosts whose `python3` is 3.12 or newer.
