Inventory collection no longer deletes a retired service while a saved task or schedule names it, on PostgreSQL deployments: each collection batch now re-reads the tasks and schedules naming services immediately before its delete, and task and schedule writes cannot land in between. A task or schedule saved *while* a batch is running is saved after that batch finishes, so it can still name a service the batch has just deleted. SQLite deployments, where collection is off by default, run it without this protection. While a batch runs, the Tasks API's task and schedule create and update requests — and every PMM Extensions page that saves a task or schedule through them — wait for it to finish, for at most 30 seconds, and otherwise answer 503 Service Unavailable with "Inventory collection is running; retry the request shortly." The Celery worker running collection now reads and deletes inventory rows directly instead of calling the Inventory API, so it must be able to reach the inventory database; the PMM-embedded side-car already shares one database across all three services.
