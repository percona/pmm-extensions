Snippet interpreters are no longer run through `env -S`: the configured interpreter command (`EXTENSIONS.SNIPPETS.INTERPRETERS`, including `INTERPRETERS_PREPEND` / `INTERPRETERS_APPEND` entries) is split on whitespace and its words are run as they are. Snippets dispatched with requirements (`task_with_requirements`, such as Python snippets running in a virtualenv) are unaffected, since that path never used `env -S`. A custom command that relied on `env -S` syntax — a leading `NAME=VALUE` assignment, an `env` option such as `-u NAME`, quoted words, backslash escapes or `${VAR}` expansion — no longer works. When that syntax is in the first word, executions are reported Unlaunchable, or Failed if the first word contains a `/` without being an absolute path (for example `PATH=/opt/bin bash`). When it is in a later word (for example `bash -c 'echo hi'`), the interpreter receives the quotes, backslashes or `${VAR}` literally, which usually fails the execution. A plain program name or absolute path with optional arguments, with or without a `sudo` prefix, is unaffected, which covers the shipped defaults. The change applies once the tasks service starts on this release. To keep leading assignments or `env` options, prefix the command with `env` (for example `env FOO=1 bash`); for anything else, point the command at a wrapper script by absolute path.
