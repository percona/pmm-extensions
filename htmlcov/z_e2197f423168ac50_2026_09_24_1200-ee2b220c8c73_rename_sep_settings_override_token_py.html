22Move the stored ``settingoverride.setting_class`` token of the service's own 

23settings class from ``SEP_SETTINGS`` to ``EXTENSIONS_SETTINGS``. 

24 

25The token is derived from the settings class name, and that class is now 

26``ExtensionsSettings``. Without this revision every existing override row for it 

27would be orphaned: nothing reads a token no live class derives, so the 

28overrides would silently fall back to their YAML defaults. 

29 

30Only this track writes rows for that class, and on a shared database the three 

31tracks share one physical ``settingoverride`` table, so the rename runs here 

32alone. Both tokens are frozen literals: the revision must keep meaning the same 

33thing whatever the class is called on the release that executes it. 

34 

35The ciphertext envelope marker moves from ``sep.enc.v1.`` to 

36``extensions.enc.v1.`` in the same release. A leaf still carrying the old marker 

37is recognised as neither marked nor bare ciphertext, so it would be read back as 

38the credential itself; every track rewrites its own table's markers, and this 

39revision does so for this one. The marker moves forward only: every earlier 

40revision's downgrade runs this release's code, which reads the new marker alone, 

41so restoring the old one would strand the downgrades below this revision.
