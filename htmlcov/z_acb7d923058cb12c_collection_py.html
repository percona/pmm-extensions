16"""Delete the inventory tombstones no persisted reference resolves any more. 

17 

18A tombstoned inventory entity may be deleted when all three of these hold: 

19 

201. **Age.** It has been retired for at least ``COLLECTION_RETENTION`` — and, 

21 while a standing identity link pins it, for ``IDENTITY_LINK_PIN_RETENTION``. 

222. **No live referent.** No artifact that can still *resolve or re-emit* its id 

23 survives. For a service that means: no ``MysqlBackupRun`` row, no ``Task.data`` 

24 meta (soft-deleted tasks included), no in-flight ``TaskHistory``, and no 

25 Celery-beat ``PeriodicTask.kwargs`` naming it. Nodes, schemas and tables have 

26 no external persisted holder at all, so this clause is vacuous for them. 

273. **Subtree safety.** Every descendant in its retirement subtree is itself 

28 collectible — enforced by :func:`app.inventory.crud.collect_retirable_entities`, 

29 which owns the walk. 

30 

31Purely *historical* references do not block collection. A terminal 

32``TaskHistory.execution_request`` meta is the only such holder: it can never 

33create a new dangling reference, and it already carries ``_service_name`` 

34unconditionally. The one path that resolves its id — the legacy form backfill — 

35reads inventory through the retired-hiding default manager, so a retired 

36service's id stops matching there the moment it is tombstoned and deleting the 

37row later changes nothing. An *in-flight* history is not historical and does 

38block, because it can still complete and write a new ``MysqlBackupRun`` row 

39naming the id. 

40 

41The scan and the delete are not one transaction. For every holder that already 

42existed when the scan ran the window is closed: ``app/tasks/run_result.py`` 

43resolves a recorder off the live ``Task`` row, so a recorder firing mid-window 

44belongs to a task the scan already read — which is why the ``Task`` scan reads 

45every row rather than only the active ones. 

46 

47A holder persisted *during* the window is covered by the reference fence 

48(:mod:`app.tasks.reference_fence`). Every Tasks API route that creates or 

49updates a task or a beat schedule — ``create_task``, ``update_task``, 

50``create_periodic_task_for_task_name``, ``update_periodic_task`` — holds the 

51fence shared across its write, and so does every PMM Extensions caller, since 

52each one writes through those routes. Each batch holds it exclusive from its 

53retained-set read through its delete, which runs in the same coroutine. So a 

54write either committed before the batch took the fence, and the batch's read 

55sees it, or it waits until the batch has finished deleting. A batch also checks 

56it still holds the fence just before its delete, and the fence's connection runs 

57with the idle-in-transaction timeout turned off. 

58 

59Knowingly outside that guarantee: 

60 

611. **SQLite deployments.** SQLite has no advisory lock, so the fence is a no-op 

62 there. Collection ships scheduled only in the PostgreSQL side-car profile; an 

63 operator who schedules it on SQLite runs it unfenced. 

642. **Writers the fence does not wrap.** The seed data, the system beat 

65 schedules and the form backfill write task and schedule rows directly, and 

66 none of them writes a ``_service_id`` holder. The Tasks API's execution 

67 routes create in-flight ``TaskHistory`` rows unfenced, but the backup-run 

68 recorder reads the service id off the live ``Task`` row, which the scan 

69 already covers. 

703. **A write naming an id the batch it waited for deletes.** A request that 

71 arrives mid-batch commits after the delete and can name an id already gone. 

72 That is the Tasks API accepting unvalidated meta, not this window, and is 

73 tracked separately. 

744. **Infrastructure failure during a fenced call.** The guarantee holds while 

75 the processes and database connections on both sides stay up. A fence 

76 backend ended or cut off *during* the delete call, or a COMMIT left in doubt 

77 by a lost connection or a dead worker, falls outside it: closing that needs 

78 the delete and the fence in one transaction across two databases. The batch 

79 holds the fence for ``REFERENCE_FENCE_COMMIT_GRACE`` after a failed delete, 

80 which covers the in-doubt case a live process survives. The writer side has 

81 the same boundary without that cover: a writer whose fence backend is lost 

82 mid-write, or whose COMMIT is left in doubt, releases the fence while its 

83 write may still land. 

84"""

125def _positive_ids(values: Iterable[Any]) -> set[int]: 

126 """Coerce raw JSON-extracted values to the positive integers among them. 

127 

128 The extraction crosses a dialect boundary — PostgreSQL hands back text while 

129 SQLite hands back the native scalar — and the source is a free-form JSON 

130 blob, so anything that is not a positive integer is a malformed envelope 

131 rather than an error to raise on. 

132 

133 :param values: The raw values read out of a ``meta`` key. 

134 :return: The positive integers among them. 

135 """ 

136 ids: set[int] = set() 

137 for value in values: 

138 try: 

139 entity_id = int(value) 

140 except (TypeError, ValueError): 

141 logger.debug( 

142 "Ignoring non-integer %s meta value %r", SERVICE_ID_META_KEY, value 

143 ) 

144 continue 

145 if entity_id > 0: 

146 ids.add(entity_id) 

147 return ids

150def _beat_kwargs_service_ids(payloads: Iterable[str | None]) -> set[int]: 

151 """Extract the service ids the beat schedules still carry. 

152 

153 ``PeriodicTask.kwargs`` is a JSON *string* column declared by 

154 ``sqlalchemy-celery-beat``, so the payload is parsed in Python rather than by 

155 a JSON operator. Every level is ``isinstance``-guarded: the column is 

156 operator-populated free text, so a malformed row is skipped rather than 

157 raised on. The extracted leaves are gathered into a list rather than a set 

158 for the same reason — the value is unconstrained JSON and may be unhashable, 

159 and judging it is :func:`_positive_ids`'s job. 

160 

161 Only the rows :class:`PeriodicTaskManager` surfaces reach here, which is the 

162 ``execute_task_by_name`` indirection. That is the sole beat shape carrying an 

163 ``execution_data`` envelope, so a row pointing straight at a Celery function 

164 cannot name a service id in the first place. 

165 

166 :param payloads: The raw ``kwargs`` strings of the beat schedules. 

167 :return: The service ids named by their envelopes. 

168 """ 

169 ids: list[Any] = [] 

170 for payload in payloads: 

171 if not payload: 

172 continue 

173 try: 

174 decoded = json.loads(payload) 

175 except json.JSONDecodeError: 

176 logger.warning("Skipping periodic-task kwargs that is not valid JSON") 

177 continue 

178 if not isinstance(decoded, dict): 

179 continue 

180 execution_data = decoded.get("execution_data") 

181 meta = execution_data.get("meta") if isinstance(execution_data, dict) else None 

182 if isinstance(meta, dict) and SERVICE_ID_META_KEY in meta: 

183 ids.append(meta[SERVICE_ID_META_KEY]) 

184 return _positive_ids(ids)

187async def collect_task_envelope_service_ids() -> set[int]: 

188 """Return every inventory service id a task envelope can still re-emit. 

189 

190 Three reads, in two databases. The first two cover every holder that existed 

191 when the scan ran; the third covers a schedule that has not fired yet. A 

192 holder written during a batch is covered by the reference fence instead. 

193 

194 A read that cannot complete propagates rather than returning what it managed 

195 to gather: a holder that could not be read is not a holder that is empty, and 

196 treating it as empty would collect the entities it names. 

197 

198 :return: The service ids the task envelopes still name. 

199 :raises Exception: Whatever a database this reads raises, unchanged. 

200 """ 

201 tasks_session_maker = get_tasks_session_maker() 

202 async with tasks_session_maker() as session: 

203 service_ids = _positive_ids( 

204 await TaskManager.envelope_meta_values(session, SERVICE_ID_META_KEY) 

205 ) 

206 service_ids |= _positive_ids( 

207 await TaskHistoryManager.in_flight_meta_values(session, SERVICE_ID_META_KEY) 

208 ) 

209 beat_session_maker = get_beat_session_maker() 

210 async with beat_session_maker() as session: 

211 service_ids |= _beat_kwargs_service_ids( 

212 await PeriodicTaskManager.values_list(session, ["kwargs"]) 

213 ) 

214 return service_ids

217async def collect_referenced_entities() -> dict[RetirableEntityName, set[int]]: 

218 """Return every inventory id PMM Extensions still holds a resolvable reference to. 

219 

220 Any failure propagates: issuing the delete with a partial retained set would 

221 collect an entity something still resolves, which is exactly the outcome this 

222 job exists to prevent. 

223 

224 :return: The referenced ids, keyed by inventory entity type. 

225 :raises Exception: Whatever a declared provider or the task-envelope scan 

226 raises, unchanged. 

227 """ 

228 referenced = { 

229 RetirableEntityName.SERVICE: await collect_task_envelope_service_ids() 

230 } 

231 extensions_session_maker = get_extensions_session_maker() 

232 async with extensions_session_maker() as session: 

233 for provider in collect_inventory_reference_providers(): 

234 for entity_name, entity_ids in (await provider(session)).items(): 

235 referenced.setdefault(entity_name, set()).update(entity_ids) 

236 return referenced

239async def clear_absence_ledger( 

240 collected: Mapping[RetirableEntityName, list[int]], 

241) -> None: 

242 """Drop the missing-grace ledger rows of the entities about to be deleted. 

243 

244 Cleared *before* the delete rather than after, because that is the only 

245 order with no crash window, and it is safe: the syncer short-circuits on an 

246 already-retired entity before it can record a fresh absence, so an early 

247 clear cannot be undone, and clearing a superset is harmless. 

248 

249 Cleared for every syncer rather than the configured ones, which is the same 

250 licence read the other way: a ledger row outlives the configuration that 

251 wrote it, so scoping the delete to ``EXTENSIONS.SYNCERS`` would leave the rows of a 

252 syncer since removed or renamed behind permanently, with the entity they 

253 name gone and nothing left that could ever reach them. 

254 

255 :param collected: The ids the dry run reported, per entity type. 

256 """ 

257 extensions_session_maker = get_extensions_session_maker() 

258 async with extensions_session_maker() as session: 

259 for entity_name, entity_ids in collected.items(): 

260 if not entity_ids: 

261 continue 

262 await SyncEntityAbsenceManager.clear( 

263 session, 

264 None, 

265 _LEDGER_ENTITY_TYPES[entity_name], 

266 *entity_ids, 

267 )

279async def run_inventory_collection() -> None: 

280 """Collect tombstoned inventory entities no live reference resolves. 

281 

282 Each batch holds the reference fence exclusive from its retained-set read 

283 through its delete, so no in-scope Tasks API write can land in between. Under 

284 the fence it reads the retained set afresh, then calls the inventory 

285 service's own collect twice with it: a dry run naming the ids, then — once 

286 their ledger rows are gone and the fence is confirmed still held — the real 

287 delete. The delete runs in this coroutine, on an inventory session of its 

288 own, so the fence cannot be released before the delete has returned or 

289 raised. Both cutoffs are computed once for the whole run so successive 

290 batches cannot drift. 

291 

292 When the real delete raises, the fence is held for 

293 ``REFERENCE_FENCE_COMMIT_GRACE`` before the error propagates: a COMMIT the 

294 server had already received may still land, and no writer may get in ahead 

295 of it. 

296 

297 :raises AdvisoryLockTimeoutError: If in-flight writes hold the fence past its 

298 bound. Raised before that batch clears or deletes anything. 

299 :raises AdvisoryLockLostError: If the fence was lost after the retained set 

300 was read. Raised before that batch's delete, after its ledger clear. 

301 :raises SQLAlchemyError: If a database the run uses fails, including a 

302 type's delete, with the deeper types' deletes of that batch already 

303 committed. 

304 :raises Exception: Whatever computing the retained set raises, unchanged — 

305 deleting against a partial retained set is the failure this prevents. 

306 """ 

307 now = utc_now() 

308 retired_before = now - inventory_app_settings.COLLECTION_RETENTION 

309 link_pin_retired_before = now - inventory_app_settings.IDENTITY_LINK_PIN_RETENTION 

310 tasks_session_maker = get_tasks_session_maker() 

311 inventory_session_maker = get_inventory_session_maker() 

312 for batch in range(inventory_app_settings.COLLECTION_MAX_BATCHES): 

313 async with ( 

314 tasks_session_maker() as fence_session, 

315 hold_reference_collection_fence(fence_session) as fence, 

316 inventory_session_maker() as inventory_session, 

317 ): 

318 collect = partial( 

319 collect_retirable_entities, 

320 inventory_session, 

321 retired_before=retired_before, 

322 link_pin_retired_before=link_pin_retired_before, 

323 keep=await collect_referenced_entities(), 

324 limit=inventory_app_settings.COLLECTION_BATCH_SIZE, 

325 on_collected=_log_collected, 

326 ) 

327 candidates = await collect(dry_run=True) 

328 await clear_absence_ledger(candidates.deleted) 

329 await fence.verify() 

330 try: 

331 result = await collect(dry_run=False) 

332 except BaseException: 

333 await asyncio.sleep(REFERENCE_FENCE_COMMIT_GRACE.total_seconds()) 

334 raise 

335 logger.info( 

336 "Inventory collection batch %s deleted %s entities", 

337 batch + 1, 

338 sum(len(ids) for ids in result.deleted.values()), 

339 ) 

340 if not result.remaining: 

341 return 

342 logger.info( 

343 "Inventory collection stopped at its %s-batch cap; the next run continues.", 

344 inventory_app_settings.COLLECTION_MAX_BATCHES, 

345 )

348async def run_scheduled_inventory_collection() -> None: 

349 """Run inventory collection, logging and re-raising any failure. 

350 

351 :raises AdvisoryLockTimeoutError: If in-flight writes hold the reference 

352 fence past its bound. 

353 :raises AdvisoryLockLostError: If a batch lost the fence before its delete. 

354 :raises SQLAlchemyError: If a database the run uses fails. 

355 :raises Exception: Whatever computing the retained set raises, unchanged. 

356 Every failure is logged and re-raised so the Celery run records it and 

357 the task's failure alert fires; aborting deletes nothing, except in the 

358 window between clearing a batch's ledger rows and its delete, and the 

359 deeper types a failing delete had already committed. 

360 """ 

361 try: 

362 await run_inventory_collection() 

363 except Exception: 

364 logger.exception("Scheduled inventory collection failed") 

365 raise
