16"""require one host observation fact 

17 

18Revision ID: a1f7c3d95e82 

19Revises: b351dd0aaed8 

20Create Date: 2026-09-21 19:30:00.000000 

21 

22Give ``hostsystemobservation`` a table-level guard for the invariant only 

23``HostSystemObservationWrite``'s validator held: at least one of ``os_version``, 

24``installed_packages``, ``config`` and ``can_elevate`` must be non-NULL. 

25 

26Rows that would violate the CHECK are deleted first, unconditionally, following 

27the remediate-in-migration principle ``e4b8c2f7a915`` established for 

28``node.external_id`` / ``service.external_id``: SEP ships as an 

29independently-deployed sidecar per customer, so there is no fleet-wide database 

30an audit could clear on every installation's behalf, and a constraint that 

31aborts somebody's upgrade is not a constraint that ships. It remediates by 

32deleting rather than by retiring and backfilling, because an absent observed 

33fact cannot be synthesized the way an identifier can. At the API layer the 

34deleted row is indistinguishable from the "never observed" case 

35``get_host_system_observation`` already answers with a 404, so removing it 

36corrects the response rather than degrading it; what is lost is the 

37``observed_at`` of a collection that returned nothing, which is why every 

38deleted row is logged at WARNING first. Nothing in a released SEP creates such a 

39row — the validator and the table landed together, and the sole producer returns 

40``None`` when no fact was collected — so this step is a pre-flight for rows 

41introduced by hand-written SQL, a restored backup or a future bug. 

42 

43``installed_packages`` and ``config`` are normalized before that deletion runs. 

44Both are JSON columns, and SQLAlchemy's ``JSON`` persisted an unset value as the 

45JSON text ``null`` rather than as SQL NULL until the model started declaring 

46``JSON(none_as_null=True)``. Such a value is not NULL, so without this step a 

47row holding no observed fact at all would read as holding two, escape the 

48deletion below, and then satisfy the CHECK for the rest of its life — the exact 

49case this revision exists to make impossible. Rewriting them to SQL NULL both 

50exposes those rows to the deletion and leaves every surviving row spelling an 

51unset JSON fact the one way the CHECK understands. The match is written as 

52``CAST(col AS TEXT) = 'null'`` because PostgreSQL's ``json`` type has no 

53equality operator, and the rewrite binds ``sa.null()`` rather than ``None``, 

54which the same bind processor would turn straight back into JSON ``null``. 

55 

56All three steps go through SQLAlchemy Core rather than raw SQL, for the reasons 

57``e4b8c2f7a915``'s docstring spells out: both supported engines — SQLite and 

58PostgreSQL, the two members of ``DatabaseDialect`` — are reachable here and 

59their spellings diverge. The CHECK is added inside ``batch_alter_table`` because 

60SQLite has no ``ALTER TABLE ... ADD CONSTRAINT``; batch mode recreates the table 

61there and emits a plain ``ALTER`` on PostgreSQL. 

62 

63Downgrade drops the CHECK and restores nothing — neither the discarded rows nor 

64the JSON ``null``s the normalization rewrote. Unlike ``e4b8c2f7a915``, whose 

65upgrade only retired and backfilled, this one genuinely discards rows: an 

66all-NULL observation carries no fact worth restoring, and a JSON ``null`` and a 

67SQL NULL both decode to ``None`` at the API, so there is nothing to put back. 

68"""

121def _holds_json_null(fact: sa.ColumnClause) -> sa.ColumnElement[bool]: 

122 """Match rows whose JSON ``fact`` holds the JSON text ``null``. 

123 

124 The comparison goes through a text cast because PostgreSQL's ``json`` type 

125 has no equality operator; the cast renders and matches on SQLite too. 

126 

127 :param fact: The JSON column to test. 

128 :return: A predicate true for rows storing JSON ``null`` in that column. 

129 """ 

130 return sa.cast(fact, sa.Text) == "null"
