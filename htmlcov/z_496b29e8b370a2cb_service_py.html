16"""Run one probe sweep: inventory, executor mapping, dispatch, facts. 

17 

18This is the half of discovery that cannot be done from PMM. Everything PMM can 

19derive for itself — identity, versions, replica-set state, reachability, load — it 

20reads from its own inventory and VictoriaMetrics. What is left needs a process on the 

21database host to answer: the command line a mongod was started with, the config file 

22it read, and above all the *installed* binary version as against the *running* server 

23the metrics report. Their divergence is the upgraded-but-not-restarted case, and no 

24metric anywhere carries it. 

25 

26The dispatch machinery lives here: :mod:`~app.extensions.apps.om_inventory.inventory`, 

27:mod:`~app.extensions.apps.om_inventory.mapping`, :mod:`~app.extensions.apps.om_inventory.dispatch` 

28and the :mod:`~app.extensions.apps.om_inventory.payload` package. An upgrade app and a restart 

29app will want exactly the same four, so they will want a shared home; this is where they 

30live until there is a second caller to justify one. 

31"""

126#: How a service's role is read off its probe record. 

127#: 

128#: Order matters: an arbiter *is* a ``mongod`` process, so it has to be tested before 

129#: the ``mongod`` fallback or it would be misclassified as one; mongos is tested before 

130#: config for the same reason — both run distinct programs, but checking the more 

131#: specific signal first keeps the table readable top to bottom. 

132#: 

133#: ============ ========================================================= 

134#: role how the record says so 

135#: ============ ========================================================= 

136#: arbiter ``database.is_arbiter`` is true (``hello.arbiterOnly``) 

137#: mongos ``process.program == "mongos"``, or ``database.msg == "isdbgrid"`` 

138#: config ``sharding.clusterRole == "configsvr"`` in ``getCmdLineOpts``, 

139#: or ``--configsvr`` in ``process.argv`` 

140#: mongod otherwise, when a server process was found 

141#: ============ ========================================================= 

142def classify_role(record: dict[str, Any]) -> str | None: 

143 """Classify a service's role from what its probe record actually saw. 

144 

145 Deliberately not from ``process.program`` alone: an arbiter is a ``mongod`` 

146 process too, and stopping there would fill the column with a value that is not 

147 wrong but is not the distinction it exists to make. 

148 

149 A config server is read from ``getCmdLineOpts``, not from the command line. 

150 ``--configsvr`` as a flag is the rarer shape: a config server is ordinarily 

151 started as ``mongod --config /etc/mongod.conf`` with ``sharding.clusterRole: 

152 configsvr`` *inside* that file, so argv carries no trace of the role at all and 

153 every config server in the estate reads as a plain ``mongod``. ``parsed`` is 

154 mongod's own resolved view of both, which is why it is the source and the flag 

155 is only a fallback for a record whose database facts did not come back. 

156 

157 :param record: One probe record for a service. 

158 :return: The role, or ``None`` when no server process was found for it. 

159 """ 

160 database = record.get("database") or {} 

161 process = record.get("process") or {} 

162 parsed = ((database.get("raw") or {}).get("cmd_line_opts") or {}).get( 

163 "parsed" 

164 ) or {} 

165 cluster_role = (parsed.get("sharding") or {}).get("clusterRole") 

166 

167 if database.get("is_arbiter"): 

168 return "arbiter" 

169 if process.get("program") == "mongos" or database.get("msg") == "isdbgrid": 

170 return "mongos" 

171 if cluster_role == "configsvr" or "--configsvr" in (process.get("argv") or ""): 

172 return "config" 

173 if process.get("running"): 

174 return "mongod" 

175 return None

262 record: dict[str, Any], 

263 fields: tuple[tuple[str, tuple[str, ...]], ...],

265) -> dict[str, Any]:

287@dataclass 

288class SweepOutcome: 

289 """Carry everything one sweep produced. 

290 

291 A dataclass, not a tuple: the counters and the per-service records are different 

292 things, and positional unpacking at a call site would say which was which only by 

293 convention. 

294 

295 :param total: Services inventory reported. 

296 :param resolved: ...of which mapped to a live executor host. 

297 :param orphaned: ...of which did not. 

298 :param answered: Services whose host returned a usable record. 

299 :param nodes: One record per mapped service; see :class:`ProbeRun`. 

300 :param hosts: The hosts in scope this sweep, whether or not they carry a service. 

301 :param host_documents: The ``observed`` document per host that answered, keyed by 

302 executor host — the level those attributes belong to. 

303 :param service_documents: The ``observed`` document per service that answered, 

304 keyed by PMM's service id. 

305 :param service_roles: The role :func:`classify_role` read off an answering 

306 service's record, keyed by PMM's service id. Absent where the record carried 

307 no server process, which :func:`~app.extensions.apps.om_inventory.crud.upsert_service` 

308 already treats as "this attempt saw nothing" and must not overwrite. 

309 :param service_errors: Why a service did not answer, keyed by PMM's service id. 

310 Only for services a run actually attempted: an entity nobody targeted must 

311 not have its timestamps touched at all. 

312 :param seen: ``(service, node_id)`` for every service PMM knows that resolved to 

313 a host in scope, orphans included — all of them get a row. 

314 :param attempted: PMM's service ids for the subset this run actually probed. The 

315 rest keep the freshness columns they already had. 

316 :param dispatched: Executor hosts a payload was actually sent to — every host with 

317 a usable executor, whether or not it serves a mapped service: a machine 

318 carrying a PMM client and no database is exactly the one an install decision is 

319 about, so it is dispatched to like any other. A host with **no** usable 

320 executor is not in here, and must not be: recording it as a failed attempt 

321 would have it accumulate a failure every sweep for a condition that is not a 

322 failure — there was nothing to dispatch to. 

323 :param host_errors: Why a host did not answer, keyed by PMM's node id. The 

324 dispatch's own error where it had one, and otherwise that it answered nothing; 

325 the estate row and the receipt both read it, so the two cannot give an 

326 operator two different reasons for one failure. 

327 """ 

328 

329 total: int = 0 

330 resolved: int = 0 

331 orphaned: int = 0 

332 answered: int = 0

337 service_roles: dict[str, str] = dc_field(default_factory=dict)

345#: How long to wait for PMM Extensions' own APIs before calling a sweep failed, and how often 

346#: to retry while waiting. 

347#: 

348#: The sweep reads the estate over HTTP from PMM Extensions itself, so a restart races its own 

349#: web server: beat's ``DatabaseScheduler`` sets "last run" to now on startup and fires 

350#: the sweep on its first tick, seconds before uvicorn has finished binding. Measured 

351#: on this workspace — the sweep dispatched 6 seconds before "Application startup 

352#: complete" and wrote a terminal ``FAILED`` carrying ``Cannot connect to host 

353#: localhost:8000``, on an estate where nothing was wrong. Both consumers lead with the 

354#: newest run, so a healthy estate presented as a failed sweep until the next tick. 

355#: 

356#: Deliberately not an operator setting: "my own web server was not up yet" is not a 

357#: condition anyone should have to tune, and a sweep that waits half a minute for it 

358#: costs nothing against a schedule measured in minutes. 

359STARTUP_RETRIES = 6 

360STARTUP_RETRY_DELAY = 5

409async def sweep(observed_at: str, node_ids: list[str] | None = None) -> SweepOutcome: 

410 """Map, probe and collect, without touching the run row. 

411 

412 Split out so :func:`run_probe` reads as the lifecycle it is — create, work,

417 recognised as a host at all, and then everything outside the scope is dropped 

418 before a single dispatch is made. Nothing outside it is written: an entity this 

419 run did not attempt keeps every timestamp it had, so refreshing one host cannot 

420 make the rest of the estate look failed. 

421 

422 :param observed_at: When the sweep began, ISO 8601, stamped on every fact.

502def _build_receipt( 

503 outcome: SweepOutcome, 

504 mapped: list[Any], 

505 host_results: dict[str, Any], 

506 node_ids: dict[str | None, str], 

507) -> list[dict[str, Any]]: 

508 """Record what the sweep attempted, one entry per **host**. 

509 

510 Host-oriented rather than service-oriented, because a sweep attempts hosts: a 

511 flat list of services would mean a machine carrying a PMM client and no database 

512 - the case OM most exists to describe - appears nowhere in it at all, however 

513 many times it is probed. A reader looking for ``pmm-client-node00`` would find 

514 the sweep counted it and could not see it. 

515 

516 One dispatch covers every service on a host, so the host owns the timing and the 

517 failure; its services carry only what is theirs. That is also why the duration is 

518 reported once, on the host, rather than repeated identically across its 

519 services, which would read as several measurements when it is one. 

520 

521 Outcomes only, deliberately: what the probe *found* belongs to the estate, where 

522 it is upserted and stays current, and carrying it here too would be a second copy 

523 that goes stale the moment the next sweep runs. ``task_history_id`` is the 

524 exception that proves it — not a finding, but a pointer to where the raw output 

525 of this attempt can still be read, in the Nomad task log the receipt itself never 

526 holds.

799def terminal_status(outcome: SweepOutcome) -> ProbeRunStatus: 

800 """Derive a sweep's terminal status from what it reached. 

801 

802 Judged on **dispatches and services together**, not services alone. Services alone 

803 was right while every dispatch existed to reach one, and it stopped being right 

804 the moment a host could be probed for its own sake: a refresh of a machine with a 

805 PMM client and no database resolves no services at all, and would have been 

806 reported ``FAILED`` for doing exactly what it was asked. Measured that way on a 

807 scoped refresh of ``standalone-node00``, which is what prompted this. 

808 

809 Orphans still do not count against a run: a service whose node runs no healthy 

810 executor is a fact about the estate, not a failure of the sweep. Reaching *nothing* 

811 is different — no host answered and no service resolved — and that is OM's 

812 infrastructure being unavailable, which is the condition the probe exists to 

813 surface. 

814 

815 "Nothing" means nothing *answered*, which is not the same as nothing being tried. 

816 Reserving ``FAILED`` for having attempted nothing at all would make a run that 

817 dispatched to twelve hosts and got twelve failures ``PARTIAL`` instead — the one 

818 status that says "look at OM itself" unreachable in the case that most needs it, 

819 and a total outage would read as "some of the estate is fine" to anything 

820 automating against it. 

821 

822 :param outcome: What the sweep produced. 

823 :return: The status. 

824 """ 

825 attempted = len(outcome.dispatched) + outcome.resolved 

826 answered = len(outcome.host_documents) + outcome.answered 

827 

828 if not attempted: 

829 return ProbeRunStatus.FAILED 

830 if answered == attempted: 

831 return ProbeRunStatus.SUCCESS 

832 if not answered: 

833 return ProbeRunStatus.FAILED 

834 return ProbeRunStatus.PARTIAL
