16"""Dispatch probe payloads to executor hosts and collect their NDJSON back. 

17 

18Rides the pre-seeded system ``run-python`` task rather than creating one per app: 

19``POST /execute/run-python`` with ``meta.target`` naming the executor host, 

20``meta.config`` carrying the payload's JSON config, and ``payload`` a ``file://`` 

21URI. This is how the ``topology`` app dispatches its collector shards. 

22 

23Results come back over **stdout**, streamed from the task-log chunk store the way 

24:meth:`~app.extensions.sync.models.BaseTaskSyncer.wait_for_task_output` does it. That 

25channel has no total size cap, unlike the 16 KB ``.pmm-extensions-run-result.json`` file. 

26 

27One dispatch per executor host, carrying every service that host serves — the 

28payload collects host-level facts once and reuses them across its targets, so 

29batching by host is both fewer Nomad jobs and less duplicated work. 

30"""

63# Bounds with_capacity_retry both ways, whichever runs out first. 

64# 

65# The wall-clock budget is the one that has to be sized deliberately: what a retry 

66# has to outlast here is the dispatch lock's stale-row sweep in 

67# `_dispatch_queue_item` (app/tasks/celery.py), which only clears a lock older 

68# than 30 seconds, so a shorter budget cannot clear an orphaned one at all. An 

69# attempt count on its own cannot express that, because attempt cost varies by 

70# four orders of magnitude: an attempt refused by an existing lock row returns a 

71# 409 in milliseconds, while one that ends in the pool's own connection timeout 

72# costs a full 10 seconds. The same three attempts therefore span anywhere from 

73# ~3s to ~33s, and the previous budget of three attempts over 1+2s of backoff 

74# could not reach 30 seconds by any path. 

75CAPACITY_RETRY_BUDGET_SECONDS = 40.0 

76# The attempt cap is the secondary bound, and stops a refusal that returns 

77# instantly from spinning through the budget. 

78CAPACITY_RETRY_ATTEMPTS = 8 

79_CAPACITY_RETRY_BASE_DELAY_SECONDS = 1.0 

80# Caps the doubling, so the tail of the budget is spent on several late attempts 

81# rather than on one long sleep that ends just as the budget does. 

82_CAPACITY_RETRY_MAX_DELAY_SECONDS = 8.0 

83 

84#: Substring `_dispatch_queue_item` (app/tasks/celery.py) puts in a 409's detail 

85#: when its own dispatch-lock row collided. Matched rather than the bare status 

86#: code so a 409 for an unrelated reason (e.g. "Queue item is not in a pending 

87#: state") still fails immediately instead of being retried into a longer hang. 

88_DISPATCH_LOCK_CONFLICT_MARKER = "DispatchLock" 

89 

90#: Matches the 409 `_raise_if_identical_task_conflict` (app/tasks/celery.py) raises 

91#: when an active queue item already carries this exact request, capturing that 

92#: item's id. Parsed out of the message because the id is not returned as a field; 

93#: see `_adopted_queue_item_id` for why it is worth parsing anyway. 

94#: 

95#: Deliberately matched on the whole phrase, not on a bare `\((\d+)\)`: the same 

96#: guard raises a second 409 that also names an id, "In-flight queue item (N) 

97#: cannot be compared ...", and that one means the requests could *not* be shown 

98#: identical, so adopting the item it names would be unsound. 

99_IDENTICAL_QUEUE_ITEM_RE = re.compile(r"Identical queue item already running \((\d+)\)")

113def _is_dispatch_lock_race(err: Exception) -> bool: 

114 """Return whether ``err`` is a same-content dispatch racing its own lock row. 

115 

116 ``_dispatch_queue_item`` computes its lock name as a hash of exactly 

117 ``{task_id, task, target, payload, meta}``, so a collision means a request 

118 with byte-identical content, this same host dispatched again, is contending 

119 with this one rather than a real conflict being hidden. Waiting and asking 

120 again is the correct response either way. 

121 

122 What the wait has to cover is not obvious, and is why 

123 :data:`CAPACITY_RETRY_BUDGET_SECONDS` is sized the way it is. The lock is 

124 deleted in a ``finally``, but that ``finally`` guards only the dispatch 

125 itself: the lock row is committed one frame earlier, inside 

126 ``DispatchLockManager.create``, and ``CRUDBase.save`` then issues a 

127 post-commit ``session.refresh`` needing a *second* checkout from the same 

128 pool. When the pool is exhausted that refresh raises, the row is already 

129 committed, and the ``try`` that would have released it was never entered. 

130 The lock is then orphaned, and nothing clears it until the caller's own 

131 30-second stale-row sweep. So the collision a retry meets here can just as 

132 easily be this probe's own failed first attempt as another dispatch, and it 

133 can outlive that attempt by the full 30 seconds. 

134 

135 :param err: The exception a retried call raised. 

136 :return: Whether it is worth retrying. 

137 """ 

138 return isinstance( 

139 err, HTTPConflictException 

140 ) and _DISPATCH_LOCK_CONFLICT_MARKER in str(err.detail)

143def _adopted_queue_item_id(err: Exception) -> int | None: 

144 """Return the id of an in-flight queue item this dispatch should adopt. 

145 

146 ``_raise_if_identical_task_conflict`` refuses a request an active queue item 

147 already carries, naming that item. It is not a failure of this host's probe: 

148 it says the exact probe being asked for is already running, so the answer is 

149 on its way and this call need only wait for it. 

150 

151 Adopting is sound because of what the guard compares before raising: same 

152 ``task``, same ``target``, the same meta clauses, and 

153 ``_encrypted_leaves_match`` over the payload. The item it names therefore 

154 produces the byte-identical result this dispatch would have produced itself. 

155 

156 Worth handling rather than retrying, because a retry cannot make the 

157 conflict go away: the item stays active for as long as the probe takes, so 

158 the attempts are spent waiting for a result already being computed and the 

159 host is recorded failed anyway. It is also reachable without a second 

160 caller, since ``with_capacity_retry`` retries the pool's 503 and that retry 

161 is not idempotent; the enqueue can land while the client sees the refusal, 

162 and the next attempt then collides with its own earlier item. 

163 

164 :param err: The exception the dispatch call raised. 

165 :return: The queue item id to adopt, or ``None`` if this is not that conflict. 

166 """ 

167 if not isinstance(err, HTTPConflictException): 

168 return None 

169 match = _IDENTICAL_QUEUE_ITEM_RE.search(str(err.detail)) 

170 return int(match.group(1)) if match else None

173async def with_capacity_retry(call: Callable[[], Awaitable[T]]) -> T: 

174 """Retry ``call`` a bounded number of times on a known-transient refusal. 

175 

176 A sweep dispatches up to ``MAX_CONCURRENT_PROBES`` hosts at once, each making 

177 its own requests to the Tasks API — exactly the burst that can transiently 

178 exhaust that process's own database connection pool (sized at 5 connections, 

179 surfaced as a 503) or race two byte-identical dispatches against 

180 the same dispatch-lock row (surfaced as a 409, see 

181 :func:`_is_dispatch_lock_race`). Either is a queueing accident, not a fact 

182 about this host's probe, so neither belongs counted alongside a real dispatch 

183 or collection failure. 

184 

185 Left uncapped this would be indistinguishable from a hang: retrying forever 

186 on a pool that stays saturated blocks the semaphore slot this host holds, 

187 which is exactly what starves the *other* queued hosts of a turn. So it is 

188 bounded two ways and stops at whichever runs out first — a wall-clock budget 

189 sized to outlast the dispatch lock's own stale-row sweep (see 

190 :data:`CAPACITY_RETRY_BUDGET_SECONDS`), and an attempt cap for a refusal that 

191 returns too fast for that budget to bound anything on its own. 

192 

193 The budget is checked against the *next* sleep rather than after it, so this 

194 never sleeps past the deadline only to give up on waking. 

195 

196 :param call: Zero-argument async callable to retry. 

197 :return: Whatever ``call`` returns, once it stops raising. 

198 :raises Exception: Whatever ``call`` last raised, once either bound is spent, 

199 or immediately for any exception neither predicate recognises. 

200 """ 

201 deadline = monotonic() + CAPACITY_RETRY_BUDGET_SECONDS 

202 for attempt in range(CAPACITY_RETRY_ATTEMPTS): 202 ↛ 216line 202 didn't jump to line 216 because the loop on line 202 didn't complete

203 try: 

204 return await call() 

205 except Exception as err: 

206 transient = _is_pool_capacity_error(err) or _is_dispatch_lock_race(err) 

207 if not transient or attempt == CAPACITY_RETRY_ATTEMPTS - 1: 

208 raise 

209 delay = min( 

210 _CAPACITY_RETRY_BASE_DELAY_SECONDS * 2**attempt, 

211 _CAPACITY_RETRY_MAX_DELAY_SECONDS, 

212 ) 

213 if monotonic() + delay >= deadline: 213 ↛ 214line 213 didn't jump to line 214 because the condition on line 213 was never true

214 raise 

215 await asyncio.sleep(delay) 

216 raise AssertionError("unreachable: the loop above always returns or raises")

387async def _release(tasks_api: RemoteAPI, task_history_id: int) -> str | None: 

388 """Drive an abandoned dispatch to a terminal status. 

389 

390 Giving up on a probe ends *this sweep's* wait; it does nothing to the queue item, 

391 which stays ``RUNNING`` with nothing left to advance it. That matters more than it 

392 sounds: the tasks API refuses to dispatch a queue item identical to one already in 

393 flight, and every sweep dispatches the same ``run-python`` to the same host with 

394 the same config — so one abandoned run makes that host answer ``409`` forever, and 

395 its facts quietly stop refreshing while the sweep still reports itself partial. 

396 Measured on the sandbox: seven such rows blocked their hosts for over an hour, and 

397 the sweeps in between looked like unreachable nodes rather than a queue that needed 

398 clearing. 

399 

400 Best-effort by design. The stop can legitimately fail — most sharply when the 

401 allocation is already gone, which is the case most likely to have caused the 

402 abandonment in the first place — and a sweep must not fail because its cleanup 

403 did. The reason comes back so the caller can say the dispatch was left in flight, 

404 because a queue item that could not be released is the one thing here that needs a 

405 human. 

406 

407 :param tasks_api: The tasks API client. 

408 :param task_history_id: The run to release. 

409 :return: The failure detail, or ``None`` when there was nothing to release or the 

410 run was released. 

411 """ 

412 try: 

413 history = await tasks_api.get(f"/history/{task_history_id}") 

414 # Not every failure after a dispatch leaves the queue item in flight — losing 

415 # the log stream of a run that already finished is a failure of collection, 

416 # not of the run. Stopping a terminal item answers 400, and reporting that as 

417 # "could not be released" would raise an alarm about a queue that is clean. 

418 if isinstance(history, dict) and history["status"] not in ( 

419 TaskHistoryStatusEnum.PENDING.value, 

420 TaskHistoryStatusEnum.RUNNING.value, 

421 ): 

422 return None 

423 except Exception: 

424 # Unreadable status is not a reason to skip the stop: the whole point is to 

425 # not leave a queue item behind, and an unnecessary stop is harmless. 

426 logger.exception( 

427 "OM inventory: could not read probe task history %s before releasing it", 

428 task_history_id, 

429 ) 

430 

431 try: 

432 await tasks_api.post(f"/history/{task_history_id}/stop/") 

433 except Exception as err: 

434 logger.exception( 

435 "OM inventory: could not release probe task history %s", task_history_id 

436 ) 

437 return f"{type(err).__name__}: {err}" 

438 logger.info( 

439 "OM inventory: released abandoned probe task history %s", task_history_id 

440 ) 

441 return None

564async def probe_all( 

565 tasks_api: RemoteAPI, 

566 mapped: list[MappedService], 

567 executor_hosts: Iterable[str] = (), 

568) -> dict[str, HostProbeResult]: 

569 """Probe every executor host in reach, concurrently. 

570 

571 Hosts come from two places and the second is the point: the executor hosts of 

572 resolved services, *and* every executor host the estate knows about. A machine 

573 with a PMM client and no database has no service to be reached through, and it is 

574 exactly the machine an install decision is about — so dispatching only to hosts 

575 that serve a service would leave the interesting ones permanently undescribed. 

576 

577 Concurrency is bounded by ``max_concurrent_probes``: each dispatch is a Nomad 

578 job, and a large estate would otherwise submit hundreds at once. 

579 

580 :param tasks_api: The tasks API client. 

581 :param mapped: Every mapped service, resolved or orphaned. 

582 :param executor_hosts: Executor hosts to probe even if they serve no service. 

583 :return: One result per executor host, keyed by host. 

584 """ 

585 grouped = group_by_executor(mapped) 

586 # ``setdefault`` rather than a union: a host that serves services must keep them 

587 # as its targets, and one that serves none is dispatched to with an empty list. 

588 for host in executor_hosts: 

589 grouped.setdefault(host, []) 

590 

591 if not grouped: 

592 logger.warning("OM inventory: no executor host to probe") 

593 return {}

602 *(guarded(host, entries) for host, entries in grouped.items()) 

603 ) 

604 return {result.executor_host: result for result in results}
