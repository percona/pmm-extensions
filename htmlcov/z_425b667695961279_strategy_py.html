16"""Define the step/state domain model and the :class:`InstallStrategy` seam. 

17 

18No persistence and no execution here on purpose: this module is pure planning 

19logic, unit-testable without a database or a Nomad connection. Two things are 

20deliberately kept out of it and live in sibling modules instead: 

21 

22- **Running anything.** :meth:`InstallStrategy.build_step` returns a 

23 :class:`StepAction` — data describing what a step needs, not an executed result. 

24 Turning that into a real Nomad job is 

25 :mod:`~app.extensions.apps.om_bootstrap.dispatch`'s job, so a strategy never touches 

26 the network or a host. 

27- **Persisting progress.** :class:`StepRecord`/:class:`HostBootstrapState` are the 

28 *shape* progress takes, not a database row — they are stored as JSON documents 

29 on :class:`~app.extensions.apps.om_bootstrap.models.BootstrapRun` (see 

30 :mod:`~app.extensions.apps.om_bootstrap.persistence`). 

31 

32The dynamic-progress requirement lives in :meth:`InstallStrategy.plan_steps`: it 

33returns the ordered step *names* a given spec will run, computed from the spec 

34rather than fixed on the class, so a run's actual step list (which can differ 

35between strategies, and within one strategy between specs — e.g. a TLS-enabled 

36spec adding a certificate step) is known before the first step starts. That is what 

37lets the UI render a real, run-specific progress list rather than a fixed one four 

38strategies would each have to fit themselves into. 

39"""

96 

97 Defaults to MongoDB's own for a member (priority 1, votes on, not hidden, 

98 no delay), so a host a run never names here gets exactly those. 

99

101 never become primary. 

102 :param votes: Whether this member gets a vote in elections. 

103 :param hidden: Whether this member is hidden from client read preference

144class BootstrapSpec(BaseModel): 

145 """Hold what one host's bootstrap needs to know to plan and build its steps. 

146 

147 Deliberately minimal — just enough to make :class:`InstallStrategy` concrete. 

148 The full Configure-step shape (replica set topology, member roles, TLS mode) 

149 is a later design pass, not guessed at here. 

150 

151 :param install_method: Which strategy plans and builds this host's steps. 

152 :param os: The target host's OS, from ``om_inventory``'s already-collected 

153 facts — not re-detected here. 

154 :param mongodb_version: The Percona Server for MongoDB version to install, e.g. 

155 ``"8.0"``. Selects the ``psmdb-<version>`` repository channel. 

156 :param replica_set_name: The replica set this host joins. ``rs.initiate`` is a 

157 run-level step and multi-host orchestration is PMM's stepper's job, not a 

158 single host's — this field is what one host's own config file needs to 

159 name. 

160 :param run_id: The bootstrap run dispatching this host's steps. Required to 

161 build ``install_package`` and every rollback step, which scope the host's 

162 ownership marker to this run. ``None`` while only planning a run's steps. 

163 :param data_path: Where mongod stores its data, e.g. ``/var/lib/mongo``. 

164 :param log_path: Where mongod writes its log file. 

165 :param port: The port mongod listens on. ``rs.initiate``'s member list and 

166 every ``mongosh`` dispatch need this alongside ``mongod.conf`` itself, 

167 since none of them assume the package's own unconfigured default. 

168 :param bind_ip: The interface(s) mongod listens on, e.g. ``0.0.0.0``. 

169 :param member_configs: Per-host election settings for ``rs.initiate``, 

170 keyed by the same host names ``hosts`` (the run's target list) uses. 

171 A host missing from this mapping — including every host, for a run 

172 that never sets it at all — gets :class:`MemberConfig`'s own 

173 defaults. 

174 """ 

175

177 os: OperatingSystem 

178 mongodb_version: str 

179 replica_set_name: str

181 data_path: str

207class StepRecord(BaseModel): 

208 """Record one step's progress, for a host or for a run. 

209 

210 The same shape serves both :attr:`HostBootstrapState.steps` (per-host) and 

211 :attr:`~app.extensions.apps.om_bootstrap.models.BootstrapRun.run_steps` (run-level, 

212 e.g. ``rs_initiate`` — see :meth:`InstallStrategy.plan_run_steps`): neither 

213 context needs a field the other doesn't, so one type covers both rather than 

214 two near-duplicates. 

215 

216 :param name: One of the names :meth:`InstallStrategy.plan_steps` (or 

217 :meth:`InstallStrategy.plan_run_steps`, or 

218 :meth:`InstallStrategy.plan_rollback_steps`) 

219 returned for this spec — not a fixed enum, since the step list itself is 

220 per-strategy and per-spec (see the module docstring). 

221 :param status: This step's current status. 

222 :param started_at: When the execution layer began this step, if it has. 

223 :param finished_at: When this step reached a terminal status, if it has. 

224 :param detail: A human-readable outcome — an error message on 

225 :attr:`StepStatus.FAILED`, or ``None`` while pending/running. 

226 :param task_history_id: The Tasks API history id backing this step's dispatch, 

227 while it is running — the execution layer's own bookkeeping, not a 

228 strategy concern. Still just data describing progress, so it lives here 

229 rather than in a separate persisted-only sibling type: one shape for 

230 planning, persistence, and API responses alike. 

231 :param attempt_count: How many times this step has been dispatched. 

232 Incremented on every dispatch, including the first — PMM's stepper reads 

233 this to enforce its decided retry policy (retry, then roll back) without 

234 needing a counter of its own, which would be lost on a leader failover. 

235 ``om_bootstrap`` only ever records the fact that a dispatch happened; 

236 deciding whether *another* one should is the stepper's call, not this 

237 field's. 

238 """ 

239 

240 name: str 

241 status: StepStatus = StepStatus.PENDING 

242 started_at: UTCDatetime | None = None 

243 finished_at: UTCDatetime | None = None 

244 detail: str | None = None 

245 task_history_id: int | None = None 

246 attempt_count: int = 0

249class HostBootstrapState(BaseModel): 

250 """Track one host's progress through its planned steps. 

251 

252 :param host: The node name being bootstrapped. 

253 :param steps: This host's steps, in the order :meth:`InstallStrategy.plan_steps` 

254 returned them — the full list is known before the first one starts. 

255 :param rollback_steps: This host's teardown steps, in the order 

256 :meth:`InstallStrategy.plan_rollback_steps` returned them — planned 

257 up front alongside ``steps`` so a fresh run already shows what rollback 

258 would consist of, even before anything fails. Every entry stays 

259 :attr:`StepStatus.PENDING` unless the stepper actually decides to roll 

260 this host back. 

261 :param finalize_steps: This host's post-coordination steps, in the order 

262 :meth:`InstallStrategy.plan_finalize_steps` returned them — planned up 

263 front alongside ``steps``, but not dispatched until every run-level step 

264 has succeeded (PMM's stepper's call, mirroring how it gates run-level 

265 steps on every host's ``steps`` first — see 

266 :meth:`InstallStrategy.plan_finalize_steps`'s own docstring for why this 

267 ordering exists at all). 

268 """ 

269 

270 host: str 

271 steps: list[StepRecord] 

272 rollback_steps: list[StepRecord] = [] 

273 finalize_steps: list[StepRecord] = []

275 @property 

276 def status(self) -> StepStatus: 

277 """Derive this host's overall status from its steps. 

278 

279 Never stored directly — a host's status is always a projection of its 

280 steps, so the two cannot drift apart the way an independently-set field 

281 could. 

282 

283 :return: :attr:`StepStatus.FAILED` if any step failed, 

284 :attr:`StepStatus.RUNNING` if any step is running or still pending 

285 with an earlier step done, :attr:`StepStatus.SUCCEEDED` once every 

286 step has succeeded or been skipped, else :attr:`StepStatus.PENDING`. 

287 ``PENDING`` for an empty ``steps`` list too — ``all()`` over an 

288 empty sequence is vacuously true, which would otherwise report a 

289 host with nothing planned as already done. 

290 """ 

291 statuses = [step.status for step in self.steps] 

292 if StepStatus.FAILED in statuses: 

293 return StepStatus.FAILED 

294 if StepStatus.RUNNING in statuses: 

295 return StepStatus.RUNNING 

296 if statuses and all( 

297 status in (StepStatus.SUCCEEDED, StepStatus.SKIPPED) for status in statuses 

298 ): 

299 return StepStatus.SUCCEEDED 

300 if any(status != StepStatus.PENDING for status in statuses): 

301 return StepStatus.RUNNING 

302 return StepStatus.PENDING

305@runtime_checkable 

306class InstallStrategy(Protocol): 

307 """Define one way to get MongoDB installed and configured on a host. 

308 

309 A strategy owns *how*; the state machine (PMM's ``om`` service, driving as the 

310 HA-leader-only stepper) owns *when* and *whether the run as a whole should 

311 continue*, and ``om_bootstrap``'s API persists the progress — neither knows 

312 or cares which strategy is running, only that every strategy answers these 

313 questions the same way. This is the "abstracted pre-check/install/configure/ 

314 test" requirement. 

315 

316 Four parallel step lists, not one: 

317 

318 - **Per-host** (:meth:`plan_steps`/:meth:`build_step`): everything a single 

319 host's own install needs, run independently per host. 

320 - **Run-level** (:meth:`plan_run_steps`/:meth:`build_run_step`): coordination 

321 that only makes sense once, for the whole run — ``rs.initiate`` and 

322 creating PMM's monitoring user both need every member up first, and both 

323 only need to run *once* (MongoDB replicates a created user to every member 

324 automatically), not once per host. The stepper dispatches these to one 

325 designated host from ``hosts`` (index 0 by convention — see 

326 :meth:`build_run_step`'s ``hosts`` parameter) once every per-host step has 

327 succeeded. 

328 - **Finalize** (:meth:`plan_finalize_steps`/:meth:`build_finalize_step`): 

329 per-host work that has to happen *after* run-level coordination has 

330 already succeeded, not before — enabling MongoDB authorization is the 

331 motivating case: creating the first user reliably requires authorization 

332 to still be *off* everywhere at the time, because MongoDB's localhost 

333 exception is unreliable once a replica set already has more than one 

334 member (confirmed against a real multi-member run, not a theoretical 

335 concern — once any privileged op on it fails once, the exception closes 

336 permanently for that mongod's whole lifetime, not just for one 

337 connection). So ``configure_mongod`` never enables authorization, and each 

338 host only turns it on for itself once ``create_pmm_monitoring_user`` has 

339 actually succeeded. The stepper dispatches these once every run-level step 

340 has succeeded — the same per-host shape as :meth:`plan_steps`, just 

341 running after run-level steps instead of before them. 

342 - **Rollback** (:meth:`plan_rollback_steps`/:meth:`build_rollback_step`): 

343 one host's teardown, planned up front alongside its forward steps so a 

344 fresh run already shows what rolling back would do (the decided 

345 partial-failure policy), even before anything fails. 

346 

347 ``build_step`` and ``build_run_step`` both take a ``params`` mapping for the 

348 one thing a strategy cannot itself supply: per-run secrets (a keyFile's 

349 content, a generated monitoring-user password). These live durably in PMM's 

350 encrypted Postgres, not PMM Extensions' — 

351 ``params`` is how the stepper hands one to a single dispatch, transiently, 

352 without ``om_bootstrap`` ever persisting the plaintext in 

353 :class:`StepRecord`/:class:`~app.extensions.apps.om_bootstrap.models.BootstrapRun`. 

354 """
