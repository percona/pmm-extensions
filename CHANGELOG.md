## [v3.10.0] - 2026-10-28

### Added

- PMM-15326: Added the Operations Inventory app, which sweeps the MongoDB estate over Nomad and serves the hosts, services and run history it collects under `/api/apps/om_inventory/`, configured through the new `EXTENSIONS.OM_INVENTORY` settings block or the app's own `/config` endpoint. The sweep is off until PMM's Operations for MongoDB switch turns it on; once on, it runs every ten minutes by default. It is activated in the shipped side-car, and the half that consumes it ships in pmm-managed, so a PMM built without `managed/services/om` reaches the endpoints with nothing reading them.
- PMM-15326: Added `DELETE /api/apps/om_inventory/hosts/{node_id}` and `DELETE /api/apps/om_inventory/services/{service_id}`, so a host or service row left behind when a node was replaced or re-registered under a new id can be cleared without waiting for the freshness columns to age it out on their own.
- PMM-15326: Added `DatabaseOptions.SCHEMA_TRANSLATE_MAP`, applied once on engine creation so every caller sharing a `DatabaseOptions` gets the same schema remapping without composing its own. Built for `om_inventory`'s `om` schema, which SQLite cannot create for real and which the PostgreSQL test lane routes per xdist worker, but available to any app whose tables need a non-default schema.
- PMM-15326: Added `GET /api/tasks/hosts/states/`, which reports every executor host the backend knows about, not only the ones a job could be placed on, with `reachable` and `driver_healthy` given separately so a caller can tell a never-onboarded host apart from one that is down or has a broken driver.
- PMM-15347: Added the Operations Bootstrap app, which provisions a one-member or three-member MongoDB replica set from Percona's packages on Ubuntu or Rocky Linux hosts, step by step over Nomad with rollback, and serves those runs under `/api/apps/om_bootstrap/` for pmm-managed to drive, activated in the shipped side-car. A run enables MongoDB authorization in a finalize phase once the first user exists, can be aborted in flight through `POST /runs/{id}:cancel`, and takes per-run data/log paths, port and bind IP plus per-member replica-set election settings (priority/votes/hidden/delay).
- PMM-15664: A replica-set member can now name its own bind address. `member_configs.<host>.bind_ip` overrides the run-level `bind_ip` for that host alone, so a three-member install can bind each mongod to its own address instead of to `0.0.0.0`. A host that sets none keeps the run's value. On every run, mongod now also listens on `127.0.0.1` unless the address already covers it, because the install's own checks connect there.
- PMM-15665: Each Operations scan in the run list now names the nodes it failed to scan, so the scan history can group consecutive scans that failed the same way and link each failure to its node.
- PMM-15742: The Operations Bootstrap app can create the customer's own MongoDB administrator with the root role, as an optional create_admin_user run step requested with create_admin_user in POST /api/apps/om_bootstrap/runs. Its username and password arrive with that step's dispatch and are not kept in the database; like every step's secrets, they exist on PMM Extensions' disk only in the step's script, until the step finishes.
- SEP-429: MongoDB PBM (Percona Backup for MongoDB) backup diagnostics snippet (`mongodb_pbm_diagnostics.sh`) that collects `pbm config --list`, `pbm list`, `pbm logs`, and `pbm status`, plus the `pbm-agent` service unit and journal, from a node involved in a backup or restore. The PBM MongoDB URI is auto-detected from the `pbm-agent` service environment and its password is redacted from the output. Optionally appends the tail of the local MongoDB server log for post-restore troubleshooting.
- SEP-435: MongoDB replica set diagnostics snippet (`mongodb_replica_set_collect.sh`) that collects `pt-summary`, server parameters, `getCmdLineOpts`, `serverStatus`, `hostInfo`, in-progress operations, `rs.status()`, `rs.conf()`, replication info and the latest oplog entry from a replica set node into a destination directory, then packs them into a tar.gz archive.
- SEP-436: MongoDB sharding status snippet (`mongodb_sharding_status.sh`) that runs `sh.status()` against a mongos router to capture the sharded-cluster topology — shards, databases, sharded collections, chunk distribution and balancer state — for support diagnostics.
- SEP-447: Add HAProxy config discovery and log extraction snippets
- SEP-518: MongoDB summary snippet (`mongodb_pt_summary.sh`) that runs `pt-mongodb-summary` against a MongoDB instance to produce a one-page diagnostic summary — build and host info, running operations, security, oplog, replica set and, for a sharded cluster, cluster-wide and per-shard balancer state.
- SEP-519: MongoDB server status snippet (`mongodb_server_status.sh`) that captures `db.serverStatus()` from a MongoDB instance — connections, opcounters, memory, WiredTiger cache and concurrency tickets, network, replication and metrics — as a single snapshot or a timed series of samples (`--iterations`/`--interval`), with optional filtering of the output to selected top-level sections (`--sections`).
- SEP-520: MongoDB current operations snippet (`mongodb_current_op.sh`) that captures `db.currentOp(true)` from a MongoDB instance — every in-progress operation, including idle and system operations — with optional filtering by `--min-secs` (long-running operations only) and `--active-only` (drop idle operations).
- SEP-521: MongoDB server build info snippet (`mongodb_server_build_info.sh`) that captures `db.serverBuildInfo()` from a MongoDB instance — server version and git revision, OpenSSL build, memory allocator, JavaScript engine, enabled modules and build environment — for support diagnostics.
- SEP-522: MongoDB command line options snippet (`mongodb_cmdline_opts.sh`) that captures `db.adminCommand({ getCmdLineOpts: 1 })` from a MongoDB instance — the argv the server was started with and the fully parsed configuration as the server applied it — for support diagnostics.
- SEP-523: MongoDB log components snippet (`mongodb_log_components.sh`) that captures `db.getLogComponents()` from a MongoDB instance — the current log verbosity level of every logging component (accessControl, command, query, replication, storage and the rest) — for support diagnostics.
- SEP-524: MongoDB profiling status snippet (`mongodb_profiling_status.sh`) that captures `db.getProfilingStatus()` from a MongoDB instance — the database profiler level, slowms threshold, sample rate and filter — for every database, or for a single database with `--database`, for support diagnostics.

- SEP-980: Database-backed runtime overrides for a curated set of hot-reloadable PMM Extensions configuration fields. Extensions and Tasks API processes refresh their snapshot every `SETTINGS_OVERRIDE.REFRESH_INTERVAL` (default 30s) and the new value takes effect on the next read. Override rows live in the per-service `settingoverride` table; the admin REST API for managing them ships in SEP-981 (a follow-up). Until then operators with direct DB access can write rows manually, but must populate `created_at` (e.g. `CURRENT_TIMESTAMP`) and `is_active` -- both columns are `NOT NULL` without a server default. The `setting_class` column accepts the SCREAMING_SNAKE storage tokens (NOT the Pydantic class names): `EXTENSIONS_SETTINGS`, `TASKS_SETTINGS`, `SNIPPETS_SETTINGS`, `MESSAGES_SETTINGS`. HOT fields per class in this release: `EXTENSIONS_SETTINGS` covers `CONNECTIVITY_CHECK_DEFAULT`, `ARTIFACT_DOWNLOAD_TTL`, `SYNC_REFRESH_TIME`; `TASKS_SETTINGS` covers `PRE_EXECUTION_CONNECTIVITY_CHECK`, `STALENESS_THRESHOLD_SECONDS`; `SNIPPETS_SETTINGS` covers `ENABLE_MANUAL_SYNC`, `PREVIEW_MAX_CHARS`, `PREVIEW_MAX_LINES`; `MESSAGES_SETTINGS` covers `LEVEL`. Inventory has no HOT fields and skips the refresher. Inventory/Tasks API endpoints, PMM endpoint, Celery-side fields, and snippets sync interval are intentionally NOT_OVERRIDABLE -- they are baked into long-lived objects that the snapshot refresh cannot reach without follow-up work tracked in SEP-1037 / SEP-1038 / SEP-1039. Caveat for `TASKS_SETTINGS` overrides: the snapshot refresher runs only inside the FastAPI lifespans, so HOT overrides for `STALENESS_THRESHOLD_SECONDS` and `PRE_EXECUTION_CONNECTIVITY_CHECK` take effect on the API-side reads only -- Celery-worker code paths (e.g. the Nomad executor's staleness check) continue to use the YAML default until SEP-1038 ships the worker-side loader.

### Breaking Changes

- SEP-1029: `POST /api/oauth/refresh` now requires an `HttpOnly` `refreshToken` cookie scoped to `/api/oauth` instead of a body field; response shape is slimmed to `{access_token, expires_in}` (no `refresh_token`, `id_token`, `token_type`, or `scope`). Pair with the new `POST /api/oauth/login` and `POST /api/oauth/logout`.
- SEP-1071: `PluginSchema` JSON wire format flipped from camelCase to snake_case (`displayName` → `display_name`, `listView` → `list_view`, `serviceTypes` → `service_types`, `minLength` → `min_length`, etc.). The coordinated frontend update ships in the same release.
- SEP-1265: Offset/limit pagination is now centralized in `app.core.pagination`: `limit=0` no longer means "fetch all", list endpoints require `limit>=1`, and `limit>200` is rejected with 422 on all shared paginated list routes (inventory, tasks, PMM Extensions gateway, etc.)—only merged task-history enforced this cap before, so integrators sending e.g. `limit=500` to `/api/inventory/` will now get 422; send explicit bounded `offset`/`limit` and iterate pages for full traversal. MySQL backups list keeps its separate `limit<=50` cap via `make_pagination_dep`.
- SEP-1477: Removed deprecated configuration with no compatibility shim. The `EXTENSIONS.PMM` / `EXTENSIONS__PMM__*` section is gone — PMM connection/auth config (`endpoint`, `frontend`, `api_key`, `verify_ssl`, `execution_target`) must now be set under the top-level `PMM` section. The per-syncer `pmm:` override under `SYNCERS` and `SYNCER_EXTRA_KWARGS` is no longer honored; PMM synchronizers read the top-level `PMM` directly. A leftover `EXTENSIONS.PMM` block or per-syncer `pmm:` key is now rejected at startup with a configuration error rather than being silently honored, forcing migration. Alerts-plugin config (`backup_interval`, `backup_retention`, `alert_folder_name`), which previously rode on `EXTENSIONS.PMM`, moves to a dedicated, alerts-owned `EXTENSIONS.ALERTS` section (`BACKUP_INTERVAL`, `BACKUP_RETENTION`, `ALERT_FOLDER_NAME`); it is runtime-overridable (DB-backed settings overrides, exported under `AlertsSettings`). Plugin `MODULE_NAME` values `backup`/`backups` are no longer remapped to `mysql_backups` and now fail module-existence validation — update `settings.yaml` to use `mysql_backups`.
- SEP-1624: The snippets list endpoint drops the `order` query parameter; request descending order with a `-` prefix on `sort` (for example `sort=-created_at`). Its default ordering also changes from newest-first (`created_at` descending) to approved-first (`-approved_at`), so clients that relied on the previous default must now send `sort=-created_at` explicitly. An out-of-allowlist `sort` value still returns 422, but the body is now a flat `{"detail": "Invalid sort key: '<key>'"}` string rather than a field-keyed validation-error list. The inventory and tasks list endpoints' `sort` parameters gain the same allowlist enum, so a client passing a plain string there must narrow it too. API clients should regenerate `@pmm-extensions/api`.
- SEP-1687: Remove the legacy server-rendered Jinja UI: all app HTML pages, the login/logout/homepage shell routes, the shared form/AJAX routers (`/inventory-api`, `/stop-task`, `/periodic`), CSRF form validation, flash messages, cookie-based session authentication and the `/static` mounts. The backend is now headless and JSON-only; error responses on non-`/api` paths return JSON instead of redirecting. Browser clients must authenticate with `Authorization: Bearer` — a session cookie alone now yields `401` where it previously redirected with `303`.
- SEP-1687: Remove the legacy `EXTENSIONS.SESSION` settings group. `GET /api/extensions/admin/settings` no longer lists `SESSION__COOKIE_NAME`, `SESSION__MAX_AGE`, `SESSION__SAMESITE`, `SESSION__SECURE` or `SESSION__PATH`; a stale `SESSION:` block in `settings.yaml` is ignored, and persisted override rows are deleted by a data migration on the `extensions` track. `SESSION_REFRESH` (the SPA's `refreshToken` cookie) is unaffected.
- SEP-1687: Remove the `EXTENSIONS.TEMPLATES_DIR` and `EXTENSIONS.STATIC_DIR` settings. The report PDF template and its logo now ship inside the report app (`app/extensions/apps/report/{templates,assets}/`) rather than in repository-root `templates/` and `static/` trees, so neither directory is configurable — or present — any more.
- SEP-1687: Remove the `MessagesSettings` settings class along with the flash-message middleware it configured. `GET /api/extensions/admin/settings` no longer lists the `MessagesSettings` group (`EXTENSIONS.MESSAGES.LEVEL`), `MESSAGES_SETTINGS` is dropped from the `settingoverride.setting_class` vocabulary, and its persisted override rows are deleted by data migrations on the `extensions`, `tasks` and `inventory` tracks.
- SEP-1778: An entity-style AppSchema (non-empty entities) that declares root-level forms, cardinality_rules, or fail_when now fails at plugin import instead of silently ignoring those keys; move them onto the relevant entity. In-tree plugins are unaffected — inventory is the only entity-style construction and sets no root form config — but out-of-tree or PMM-side plugins that relied on the old ignore behaviour must relocate root form config onto each entity before upgrading.
- SEP-1792: `percona/pmm-extensions:X` is the frontend-less, app-restricted PMM-embedded image, published from this release on. `percona/percona-sep` keeps the standalone product: every tag published there, `:latest` included, stays standalone, and v0.13.1 is the final standalone release. The `sep_installer.sh` installer and the `-sidecar`/`-embedded` variant tags are retired.
- SEP-1838: State-changing API requests (POST, PUT, PATCH, DELETE) now require an administrator. Non-admin users keep full read access; deployments whose non-admin users write through the API must grant them admin. Under Grafana-backed auth this makes Editors read-only alongside Viewers, since only the server-admin flag or an org Admin role maps to admin. Where PMM Extensions is embedded in PMM, the restriction takes effect only once PMM exchanges each session for a per-user PMM Extensions bearer; until then every embedded request arrives as the internal service principal and no per-user restriction applies.
- SEP-1848: A custom auth provider (`AUTH__PROVIDER__CUSTOM__PROVIDER_CLASS`) must now set `role` (`app.core.auth.models.UserRole`) on every identity it constructs; `is_admin` is derived from the role and is no longer a settable field, so an unmigrated provider fails validation at authentication time.
- SEP-1849: Session assertions minted before this release carry no role claim and are refused rather than downgraded to a role derived from the admin flag. The upgrade effect depends on the deployment shape: a standalone Grafana-auth SPA session ends and the user signs in again, because both the in-memory access token and the `refreshToken` cookie are refused; a PMM-embedded session renews itself from the ambient Grafana session with no user action; and Casdoor deployments are unaffected, because Casdoor mints no PMM Extensions assertion. No new configuration is required.
- SEP-1854: Inventory node and service writes now require a PMM origin (`external_id`, plus `source` for nodes), so a request that omits or nulls one is rejected with 422. Pre-existing rows without an origin are retired by the migration rather than deleted: they leave the active inventory views but stay resolvable through retired-inclusive reads.
- SEP-1855: Inventory node and service writes under `/api/inventory/` are now restricted to the internal service principal: `POST /nodes/`, `PUT /nodes/{id}`, `DELETE /nodes/{id}`, `POST /nodes/{id}/revive`, `POST /nodes/{id}/services/`, and the matching `PUT /services/{id}`, `DELETE /services/{id}` and `POST /services/{id}/revive` answer 403 for an **admin** user token. Lower-ranked human tokens were already refused by the app-level role gate, so only admins see a change. Syncer writes are unaffected — they authenticate with `EXTENSIONS_INTERNAL_TOKEN` and are admitted by identity. Reads and lists are unchanged.
- SEP-1856: Manual inventory authoring is removed: POST /api/apps/inventory/{entity}/, PUT and DELETE /api/apps/inventory/{entity}/{item_id} no longer exist, and the four inventory entity schemas no longer declare create forms or row actions. The syncers are the source of truth for the catalog: PMM supplies nodes and services, and the MySQL syncer discovers schemas and tables from the database itself. The inventory service's own write routes under /api/inventory/ are unchanged, so syncer writes keep working. Sync and connectivity checks are unaffected.
- SEP-1857: `DELETE` on an inventory node, service, schema or table now retires the entity and its descendants instead of deleting them; the rows survive and stay readable with `include_retired=true`, and a new `POST /{id}/revive` clears retirement. No inventory entity is permanently removed until collection lands in SEP-1892. Revival is reachable through the Inventory API only — the admin UI still presents the operation as a permanent delete and has no revive action of its own.
- SEP-1862: The inventory browser page is removed with no replacement UI, and with it five read routes under /api/apps/inventory/: GET /{entity}/, GET /{entity}/{item_id}, GET /nodes/{node_id}/system-observation, GET /services/{service_id}/system-observation and GET /schema. Those paths are no longer registered, so every verb on them answers 404. Read the catalog from the inventory service's own routes under /api/inventory/, which are unchanged; API clients must regenerate @pmm-extensions/api. Sync, sync status, syncer discovery and connectivity checks under /api/apps/inventory/ are unaffected.
- SEP-1923: MySQL is no longer a supported PMM Extensions backing-store engine. Alembic cannot build the schema on MySQL 8 (SEP-1693), so no deployment ever finished starting on MySQL; this release removes the unreachable code paths instead. Product-side MySQL features (MySQLSyncer, mysql_backups, topology) are unaffected. The supported engines are now sqlite (development and test default) and postgresql (production).
- SEP-1948: Three more inventory writes under `/api/inventory/` are now restricted to the internal service principal and answer 403 for an **admin** user token: `PUT /nodes/{id}/system-observation`, `PUT /services/{id}/system-observation` and `POST /services/{id}/schemas/`. Only the syncers, which authenticate with `EXTENSIONS_INTERNAL_TOKEN`, write through them, so syncer writes are unaffected. Any write route added to the node or service API later is syncer-only unless it is explicitly exempted; the node and service identity-link decisions stay the only exemptions and keep their current access.
- SEP-1954: Upgrading needs every Inventory API instance stopped before the inventory migration runs. A rolling upgrade that leaves the previous release recording sync health after the migration lets a late success clear a failing run that a newer failure opened; restart all Inventory instances together instead.
- SEP-1966: Snippet interpreters are no longer run through `env -S`: the configured interpreter command (`EXTENSIONS.SNIPPETS.INTERPRETERS`, including `INTERPRETERS_PREPEND` / `INTERPRETERS_APPEND` entries) is split on whitespace and its words are run as they are. Snippets dispatched with requirements (`task_with_requirements`, such as Python snippets running in a virtualenv) are unaffected, since that path never used `env -S`. A custom command that relied on `env -S` syntax — a leading `NAME=VALUE` assignment, an `env` option such as `-u NAME`, quoted words, backslash escapes or `${VAR}` expansion — no longer works. When that syntax is in the first word, executions are reported Unlaunchable, or Failed if the first word contains a `/` without being an absolute path (for example `PATH=/opt/bin bash`). When it is in a later word (for example `bash -c 'echo hi'`), the interpreter receives the quotes, backslashes or `${VAR}` literally, which usually fails the execution. A plain program name or absolute path with optional arguments, with or without a `sudo` prefix, is unaffected, which covers the shipped defaults. The change applies once the tasks service starts on this release. To keep leading assignments or `env` options, prefix the command with `env` (for example `env FOO=1 bash`); for anything else, point the command at a wrapper script by absolute path.
- SEP-1972: ENCRYPTION_KEY is now required in every environment, local development included: PMM Extensions, its Celery workers and its Alembic migrations all refuse to start until it is supplied. Existing installations must add one before upgrading, except deployments of the PMM side-car, which provisions the key itself. See the Configuration Changes entry for how to generate and supply it.
- SEP-2043: A MySQL restore whose encryption declaration disagrees with its backup type is now rejected with a 422 instead of being accepted. Three shapes are affected: an AES-256 key file named without declaring an AES-256 or dual encryption format, an AES-256 or dual format declared without naming a key file, and an AES-256 or dual format declared for a Mydumper or Binlog restore. API clients have to declare the encryption format matching the backup they are restoring and name the key file that format reads; stored restores carrying any of the old shapes are repaired when the edit form is served, so no existing task is left unopenable.
- SEP-2056: MySQL and MongoDB restores can no longer be scheduled. Both restore apps stop offering scheduling, which hides every schedule control for them in the PMM Extensions UI and in the PMM Extensions UI embedded in PMM. The PMM Extensions periodic-task gateway now answers `400 Bad Request` to `POST /api/extensions/periodic-tasks/{task_name}/` and `PUT /api/extensions/periodic-tasks/{id}` when the schedule would run a task that no installed app offers scheduling for — restores included, and likewise a task whose owner matches no installed app or is the default `ANY` — so a restore schedule can no longer be created, edited, re-enabled or disabled through that gateway. Listing and deleting schedules are unchanged, and the periodic routes of the Tasks service itself (`/api/tasks/`) are not guarded. Existing schedules of installed apps that do not offer scheduling (today the two restore apps) are not deleted: each is switched off at the first PMM Extensions startup after the upgrade, not at install time, logged at warning level by name, and stays stored until deleted. A running Celery beat stops firing it on its next schedule check, without a restart; until that PMM Extensions startup it keeps firing. A restore app already removed from `EXTENSIONS.APPS` is not swept, so its schedules keep their state. If that startup sweep cannot reach the Tasks database — a deployment whose `extensions` migrations have run ahead of its `tasks` migrations, for instance — PMM Extensions starts normally and logs the failure instead of refusing to boot, and the sweep runs at the next startup.
- SEP-2065: A task syncer's TASK_EXECUTION_TIMEOUT or TASKS_EXECUTION_WAIT_INTERVAL set to zero or a negative number is now rejected when settings load, whichever surface configured it: a SYNCERS entry in settings.yaml, JSON in SEP__SYNCERS, or a SEP__SYNCER_EXTRA_KWARGS__ env leaf. Both previously loaded as bare integers and only reached a constructed syncer, where a zero wait interval polled a running task without ever timing out and a zero timeout declared it timed out without polling it. A deployment configuring either value has to correct it before upgrading: SEP now refuses to start, naming the field and the syncer.
- SEP-2133: Removed `POST /transform/` and `POST /history/` from the tasks API. A client still calling either now gets `405 Method Not Allowed`; for `/transform/` it arrives after a `307` redirect to `/transform`, so a client that does not follow redirects sees the `307` instead. Task-history rows are recorded only by task dispatch, and `GET /history/` and the other `/history/...` routes are unchanged.

It does not fall back to the access-token lifetime, because the documented sign-out and role-change bound derives from it. Note that EXTENSIONS__AMBIENT_SESSION_SSO_ENABLED now gates embedded-UI authentication as well as standalone SPA auto-login, so turning it off in a PMM-embedded deployment signs the embedded UI out.

- SEP-1972: PMM Extensions now requires an ENCRYPTION_KEY setting in every environment, supplied as an environment variable or as a file named ENCRYPTION_KEY under SECRETS_DIR (the PMM side-car mints and persists one when neither is supplied); it has no default, is never derived from SECRET_KEY, and no value ships in the repository. It is read when the periodic schedule is seeded at startup, so a change takes effect after a restart, not through a runtime override; set it to `null` to turn the probe off and leave finished runs to the sweep.
- SEP-2131: New AUTH__PROVIDER__GRAFANA__SERVICE_ACCOUNT_BEARER_REVOCATION_WINDOW (default 5 minutes; must not be negative, rejected at startup otherwise) is the revocation window for Grafana service-account bearers: how long a revoked, disabled or re-roled service account keeps its previous verdict on new requests. 0 re-verifies against Grafana on every request.

A deployment that still sets it, in YAML or the environment, keeps starting and the value is ignored.

- SEP-937: The `SEP__PMM_FRONTEND` environment variable has been removed. Use `PMM__FRONTEND` (top-level) or `SEP__PMM__FRONTEND` (nested under SEP.PMM) instead.
- SEP-988: `_raise_if_identical_task_conflict` dedup comparison on PostgreSQL is now type-strict for scalar meta values, replacing a type-loose `str(raw_value)` text comparison. A dispatch with `meta.key = 1` (int) no longer deduplicates against a pending task with `meta.key = "1"` (string), and vice versa. Bool and `None` scalar meta values were previously not deduplicated correctly on PostgreSQL (latent bugs in `str(True) == "True"` vs jsonb text output `"true"`, and `str(None) == "None"` vs jsonb `NULL`); they are now correctly deduplicated via jsonb containment.
- SEP-988: `_raise_if_identical_task_conflict` dedup comparison on PostgreSQL is now order-insensitive for dict-valued meta items. Two dispatches whose dict-valued meta items contain the same keys/values in different insertion orders were previously considered distinct and are now considered duplicates. MySQL and SQLite dedup semantics are unchanged.
- SEP-1069: `TASKS.INVENTORY_SYNC_API_KEY` removed; replaced by `SEP_INTERNAL_TOKEN` env var. Affects only operators tracking v0.12.0 RCs (never shipped stable).

- SEP-935: Added `TASKS.PRE_EXECUTION_CONNECTIVITY_CHECK` setting (disabled/warn/block) to control pre-execution connectivity checks before task dispatch
- SEP-988: Upgrades that cross this revision run `ALTER TABLE taskhistory ALTER COLUMN execution_request TYPE jsonb USING execution_request::jsonb`, which rewrites every row in the `taskhistory` table under an `ACCESS EXCLUSIVE` lock on PostgreSQL. Expected downtime impact is proportional to row count (approximately one minute per two million rows on typical production hardware); size the upgrade window accordingly for deployments with large `taskhistory` tables. The Tasks API also fail-fasts at startup if the column is still plain `json` after deploying SEP-988, with a clear remediation message pointing to the migration.
